# Multi-console WebSocket contract (`/v1/console`)

What the operator UI sends and expects on the interactive-console socket. The web
client (NIM-146) is built against this; the Keeper endpoint (NIM-143) has to meet
it or the contract has to change on both sides at once.

Source of truth in code: `src/api/consoleProtocol.ts`.

## Connection

```
GET /v1/console
Upgrade: websocket
Sec-WebSocket-Protocol: soul-stack.console.v1, bearer.<jwt>
```

- **Auth** travels as a second subprotocol, not a query parameter: the browser
  `WebSocket` API cannot set an `Authorization` header, and a query token ends up
  in access logs and `Referer`. Same gap as the SSE run-stream (`src/api/runEvents.ts`),
  solved without leaking the token into URLs.
- The server **must** select and echo back `soul-stack.console.v1` as the
  negotiated subprotocol.
- Without the `soul.console` permission the upgrade should be refused (HTTP 403),
  or accepted and answered with a socket-scoped `error` frame — the UI handles
  both.

## Multiplexing

One socket carries N sessions. `session_id` is **generated by the client** so an
`open` can be correlated with its `opened` without a round trip. The client
guarantees uniqueness within a socket.

## Frames

All frames are JSON text. Byte payloads (`data`) are **base64** — a PTY carries
arbitrary bytes (ANSI escapes, partial UTF-8 runes, NUL) and JSON cannot hold
them raw. Fields mirror the keeper↔soul proto oneofs 1:1, so Keeper relays
rather than translates.

### Client → Keeper

| type | fields | notes |
|---|---|---|
| `open` | `session_id`, `sid`, `cols`, `rows`, `shell?` | `cols`/`rows` are a provisional 80×24; a `resize` with the measured geometry follows as soon as the pane has laid out. |
| `stdin` | `session_id`, `data` | base64; sent per keystroke, so it must not be batched into lines by the server. |
| `resize` | `session_id`, `cols`, `rows` | Sent on first fit and on every geometry change (layout switch, pane expand, window resize). Must reach `TIOCSWINSZ`. |
| `close` | `session_id` | Operator detached one pane; the other sessions on the socket stay live. |

### Keeper → Client

| type | fields | notes |
|---|---|---|
| `opened` | `session_id`, `sid`, `pid?` | Until this arrives the pane shows "connecting" and refuses input. |
| `chunk` | `session_id`, `stream` (`stdout`\|`stderr`), `data` | base64. Chunk boundaries are free — the client re-joins split UTF-8 runes. |
| `exit` | `session_id`, `code` | Pane stays on screen with an `exit N` badge; scrollback is preserved. |
| `error` | `session_id?`, `code`, `message` | With `session_id` — that pane only (RBAC deny, soul offline). Without — socket-scoped (auth/handshake). |

Unknown message types are ignored by the client, so the server may add frames
later without breaking older UIs.

## Lifecycle expectations the UI relies on

- **Kill on disconnect.** When the socket drops, Keeper reaps every PTY bound to
  it. The client acts on this: it marks all sessions `closed` and never resumes
  them. Reconnect opens *fresh* shells, and the UI says so.
- **`close` is per session**, socket close is per operator.
- **Backpressure** is the server's call (cap/coalesce/drop-with-counter). The
  client renders whatever arrives; a `chunk` flood degrades rendering, not
  correctness.

## Entry points

The page lives under Run at **`/run/console`**. It always opens on a scope step —
incarnation / coven / VM-name pattern / soulprint — and connects only when the
operator presses Connect. A link may pre-fill that form:

| link | scope form pre-filled with |
|---|---|
| `/run/console?incarnation=mongoshard` | that incarnation |
| `?target_coven=payments` | that coven |
| `?target_sids=a,b` | a pattern matching exactly those SIDs |
| `?target_glob=` / `?target_regex=` | that VM-name pattern |
| `?target_soulprint=os.family%3Ddebian` | that soulprint filter |

`target_where` (raw CEL) is **not** carried: the browser cannot evaluate it, and
carrying it would imply a narrowing the form does not apply.

**A link never connects on its own.** Opening root shells is an explicit act, not
a side effect of following a URL.

## Grouping

Groups are **defined by the operator**, not chosen from a fixed list. A group is
a name plus a query over the connected VMs, authored either as text or through
the builder — both edit the same string, so they round-trip exactly.

```
trait.role = data
coven = payments and sid ~ mongo-.*
choir = control or trait.tier = infra
```

Fields: `sid`, `coven`, `choir`, `status`, `transport`, `trait.<key>`.
Operators: `=` `!=` `~` `!~` (`~` is an anchored regex, like the scope form's
VM-name field). Conditions join with `and` or `or` — flat, no nesting, which is
what keeps text and builder equivalent.

"Split by <field>" seeds one ordinary group per value as a starting point.

Each group is a tab with **its own command input**, so a line typed for one
group cannot be sent to another. Consoles no group claimed get a trailing tab of
their own — they are hosts the operator still has to work with.

Groups are **mutually exclusive**: a console belongs to at most one, and
overlapping queries are resolved by definition order (first match wins, reorder
to reprioritise). The tab counts therefore partition the wall, so "sent to N"
needs no checking for double delivery.

Within a tab each console carries a checkbox, held **per tab**: un-armed VMs are
visibly stood down and sit out that tab's sends, while still accepting direct
typing into their terminal, and unticking a host in one tab leaves it armed in
the others. Select-all/clear are scoped to the active tab. With nothing armed
the send is refused with an explicit warning rather than silently doing nothing.

`choir` as a field needs `GET /v1/incarnations/{name}/choirs` + `…/voices`
(permission `choir.list`) and is offered only when the scope names one
incarnation; without it the rest still works.

Grouping is **browser-side only**: a tab send is N ordinary `stdin` frames, so
Keeper needs no notion of groups on the socket.

Groups and wall density (columns / terminal font size / row height) persist in
localStorage. Font size changes are pushed to the PTY as an ordinary `resize` —
smaller glyphs mean more columns, which is the point.

## Dev

`vite.config.ts` proxies `/v1` with `ws: true`, so `ws://localhost:5173/v1/console`
reaches `VITE_KEEPER_API` in dev.

`/ui/run/console?transport=mock` swaps in a browser-simulated shell
(`src/api/consoleMockTransport.ts`) for UI work without a backend. It is opt-in
only and never a fallback — an automatic mock would let a simulated shell pass
for a real host. The page shows a permanent banner while it is active.
